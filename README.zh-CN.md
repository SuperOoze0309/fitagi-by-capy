# FitAGI by Capy

面向 Android 的免费开源训练与饮食记录应用，本地优先。吉祥物是一只布偶猫，用代码画出来，而不是打包一张图片。

- **没有账号，没有服务器，没有云同步，没有广告，没有埋点。**
- 所有核心功能都能完全离线使用。
- **AI 是可选的。** 关掉 AI，它仍然是一套完整的训练记录工具；AI 层只是在此基础上提供便利。

记录体验的目标是像*笔记加训练日志*：打开，记一组，关掉。计划范围内的功能已经全部完成（0.9.0）：手动记录、本地持久化、历史、带进步曲线的动作历史、kg/lb、可选照片分析的饮食记录、可选的纯本地个人资料、四套配色主题（手绘像素吉祥物和配套景物）、完整的界面翻译（简体中文、英文、西班牙文）、JSON 备份与恢复、Markdown/CSV 导出、用户自己的别名规则、带预览与确认的自然语言快速记录、异常值复核、多层总结、提醒、训练计划，以及可选的 OpenAI 兼容 AI 层。

## 快速开始（浏览器）

```bash
npm install
npm run dev          # http://localhost:5173
```

浏览器开发通过 IndexedDB 走的是 Android 上 SQLite 用的同一套仓储接口，所以两端行为一致。

如果设备语言属于已内置的三种之一，界面会直接以该语言启动；在设置里切换语言和主题立即生效，无需刷新，也不用重启。默认主题是 `ragdoll`（布偶猫），`bunny`、`panda` 和 `orca` 一并提供。

## 构建 Android APK

```bash
npm run android:apk    # 构建 Web 资源、同步 Capacitor、打包 debug APK
```

如果想自己一步步来，这三步可以拆开：

```bash
npm run build                              # 类型检查 + 构建 Web 资源
npm run cap:sync                           # 把资源和插件复制进 Android 工程
cd android && gradlew.bat assembleDebug    # 打包 debug APK
```

APK 输出在 `android/app/build/outputs/apk/debug/app-debug.apk`。

安装到设备或模拟器：

```bash
adb install -r android/app/build/outputs/apk/debug/app-debug.apk
```

环境要求：JDK 17+（已在 21 上验证），以及带 **platform 35** 和 build-tools 的 Android SDK。Gradle 由 wrapper 提供，首次运行时会自行下载。

## 验证

```bash
npm run verify         # lint + typecheck + test + 生产构建
npm run test           # 271 个单元测试，53 个测试套件（node --test）
npm run test:browser   # 无头 Chrome 在手机和桌面两种视口下驱动真实应用
```

浏览器冒烟测试在手机视口下执行 165 项检查，在桌面视口下执行 166 项检查。

npm 脚本有 `dev`、`build`、`preview`、`test`、`test:browser`、`typecheck`、`lint`、`verify`、`cap:sync`、`cap:copy` 和 `android:apk`。

## 目前可用的功能

**首次启动**
- 全新安装会先走一个两步的权限引导：先是相机与相册，然后是通知。每一步都会在弹出系统授权框之前说明这个权限是*用来做什么*的，两步都可以拒绝，没有任何功能被权限卡住
- 早于这个引导的旧安装会跳过它，所以升级不会再次询问

**提醒**
- 由手机本地调度的通知，不经过服务器：一个时间点，加上任意几个星期几，或者每天
- 六种类型（训练、饮食、喝水、称重、休息、自定义），区别只在于标签文案和点击后跳向哪里
- **可以手动添加，也可以让 AI 根据你的目标、活动水平和实际训练时间推荐 3～5 条**；挑出想要的，它们会以可编辑提醒的形式创建出来
- 每次启动都按列表重建调度，所以重启手机、恢复备份或者稍后才授予权限，都不会让两者脱节
- 不向任何地方发送数据；通知在本机生成

**训练计划**
- 一份周计划：七天，每天有训练名称、动作、组数、次数处方（「8-10」「5」「AMRAP」—— 是文本，不是数字）以及可选的目标重量
- 休息日也是计划的一部分，不是计划里的空档
- 同一时间只有一份计划处于启用状态；首页显示今天的安排，点「开始训练」就会新建一次已经带好这些动作的训练
- **让 AI 起草**：描述你想要什么（「一周四天，上下肢分化，大约一小时」），模型草拟出一周安排，先给你过目，确认之后才会保存
- 计划不会碰你的历史：删掉一份计划，从它记录下来的每一次训练都还在

**首页**
- 开始训练 / 继续未完成的训练
- 最近的训练，带组数、容量和时长
- 今天的饮食与热量合计，以及一键「记录一餐」
- 快速记录入口

**训练** —— 最核心的界面
- 新建训练；它会立即保存，刷新页面后可以接着记
- 输入名字就能添加任意动作 —— 应用不内置动作库
- 快速加组：新组继承上一组的重量、次数、RPE、RIR 和休息
- 重量、次数、RPE 可以行内输入数字，另有休息和 RIR
- 单组标记：力竭、热身、递减组
- 复制上一组，复制任意一组，删除组
- 调整动作顺序，标记超级组，添加备注，记录平均心率
- 实时计时；「完成并保存」定格时长并把这次训练移入历史
- 完成弹层给出三种出口：**继续训练**、**完成并保存**和**取消这次训练**。取消需要确认，确认后草稿才会被删除 —— 这也是删除草稿的唯一方式；标题栏的「首页」按钮是刻意把这次训练挂起，方便之后继续
- 重命名动作，并可一步**记住为别名规则**

**饮食** —— 关掉 AI 也能用的饮食记录
- 手动录入：名称、份量、热量、蛋白质、碳水、脂肪、时间和备注，还有明细拆分，每条食物各自带自己的数字。一餐的总量始终等于各明细项之和，所以标题数字和明细不会打架
- 照片可以来自相机或相册，在本机压缩（最长边 1280 px，JPEG 质量 0.72），以 data URL 存进独立的键值存储，一餐一行；删掉这一餐，照片也一起删掉
- 配置了支持视觉的模型后，可以**用照片让 AI 估算**。估算结果以可编辑草稿的形式给出，并标注这是估算值而不是实测值，点「确认并保存」之前不会写入任何数据
- **修正对话**可以就地修改估算结果：「米饭大概 150 克」只会重算那一项，而不是从头再来，你没有提到的项目保持原样。每条修正都走同一个可编辑表单
- 饮食记录按本地日期分组，每页 40 条。顶部卡片汇总今天的热量、蛋白质、碳水和脂肪，每一天显示当天的热量合计，搜索会匹配记录名称、备注和明细项名称
- 照片**不会**进入备份：恢复后的一餐保留数字，丢掉图片
- 当已知配置的模型只支持文本时，应用会当场说明，手动表单照常可用

**个人资料** —— 可选，只保存在本机
- 昵称、性别、年龄或生日、身高、体重、目标体重、单位制（公制或英制）、训练目标和活动水平。每个字段都可以留空
- 会浓缩成一段简短的 `## User profile` 块，附在饮食分析请求上，所以让模型估算一餐并不等于要把整份历史发出去
- 资料页会把这段块原样显示出来，跟实际发送的内容一致
- **性别只是给 AI 的上下文，别无他用。** 它不影响主题、配色、图标、吉祥物或任何行为；有测试断言设置里不带 `gender`，资料里不带 `theme`
- 生日按本地日历日期解析，所以位于 UTC 以西的时区不会让年龄差出一天

**快速记录** —— 自然语言，AI 可选
- 可以输入 `卧推 60kg 8次 4组 最后一组力竭`、`bench 80 8 8 7 6 rir2`、`倒蹬577lb 8次4组` 或 `深蹲 100kg 5x5`
- **离线解析器先跑**，不依赖任何模型就能处理这些输入；解析不了才会去问那个可选的模型
- 结果始终是**预览**：每个动作和每一组都能编辑，可以取消勾选某些组，确认之前不会有任何内容进入存储
- 如果什么都解析不出来，这段文字会作为训练备注保留下来，而不是被丢弃
- 通过快速记录保存的训练直接以已完成状态进入历史，不会留下一个打开中的会话

**历史**
- 按本地日期分组，最新的在前，分页加载，多年的记录也不会变慢
- 可搜索动作名和训练备注
- 打开一次训练，编辑它的开始/结束时间和备注，删除它
- 重新打开已完成的训练继续记录，或者把它改回进行中
- 点任意动作名即可打开它的完整历史

**动作历史**
- 最佳组、训练次数、总组数、PR 次数和最近一次训练日期
- **PR 徽章**标出每一次刷新最大重量的训练，并显示相对上一次的变化
- **进步曲线**带坐标轴标签和数值读数，可在**最佳组**和**估算 1RM**之间切换 —— 后者让一个大重量三组和一个轻重量的十次组可以横向比较
- 按次列出记录，包含组数、容量、估算 1RM 以及相对上一次的增减

**别名规则**
- 完整的管理界面：新建、编辑、删除、列表
- 记录过程中重命名动作时也会自动创建（「bench」→「Bench Press」）
- 匹配不区分大小写，最长匹配优先
- 规则只影响*之后的新记录*；过去的训练保留你当时输入的原文
- 规则的优先级永远高于任何 AI 建议

**训练总结** —— 多层，在本机生成
- **每日**：练了什么（「练了腿和肩。」）、主要动作及其数字（`Leg Press: 100kg × 8 × 4`）、训练次数、正式组数、容量、时间，以及相对自己此前最好成绩的明显变化（`+5kg vs before`）
- **每周**：由各天汇总而来 —— 训练次数、相对上一周的容量变化、主要动作，以及每天一行
- **每月**：由各周汇总而来，所以一个月不是整月 JSON 堆在一起
- **不依赖任何模型**生成；LLM 只能在之后改写措辞
- 在总结页可以浏览这三种粒度，并有「重建」动作，从历史重新生成
- 启动时会补齐当前和上一周/月缺失的总结，所以通过导入进来的历史同样会被总结
- **用 AI 润色**（可选）会改写文字；本机生成的文本始终保留，一键即可恢复；AI 关闭时按钮显示「润色（AI 已关闭）」而不是消失
- 派生数据：删除一条总结永远不会影响它来自的那些训练

**异常值复核**
- 明显超出你自己历史范围的重量会在保存前被标出：弹层显示这个数值和你平时的区间，并提供**修正为**、**保持原样**或**忽略这条提醒**
- 它从不阻止保存，也从不改写数字 —— 除非你输入替换值，`600 kg` 就还是 `600 kg`
- 结构化记录和快速记录都会走这套检查
- 至少要有三次历史训练它才会开口，所以早期不会来打扰你

**AI（可选，默认关闭）**
- 任何 OpenAI 兼容端点：Base URL、API Key 和模型都由你设置
- 三种角色，系统提示词各不相同：
  - **记录员** —— 负责解析和查询，不给建议。
  - **提醒员** —— 你上次练了什么：重量、次数、RPE、趋势。
  - **教练** —— 可以给建议，但必须把回答拆成已记录的 **FACTS** 和自己的 **SUGGESTION**
- **是对话，不是表单**：回答从端点流式返回时逐字出现在屏幕上，气泡随之变高，会话记录跟着滚动。输入框像聊天应用一样固定在底部，并随输入内容增长到一定高度。已经向上滚动过的记录会停在你放的位置，不会被拽回底部
- 忽略流式开关的端点也能用：整段回答一次性出现，而不是报错
- 发现的动作名会带着本次会话中的名称一起给出
- **总结近期训练**动作可以直接要求对已构建的上下文做一段回顾，不需要提问
- **上下文构建器**决定发送什么：进行中的训练、你问到的动作最近 3～5 次训练、最近 7 天，以及周/月汇总 —— 从来不是整个数据库。每条回答都会显示这次发送了什么。
- 关闭 AI 时，AI 页面会说明怎么启用，并指向离线的快速记录
- 报错是可处理的：密钥被拒、Base URL 写错、主机不可达，各自给出具体的提示
- **视觉能力是探测出来的，不是假设的。** 模型名会按已知的模型家族归类为 `supported`、`unsupported` 或 `unknown`，你也可以在设置里覆盖这个判断。已知只支持文本的模型绝不会收到照片；`unknown` 允许你试一试，如果端点用一段自然语言拒绝，应用能识别出来并说明该模型不接受图片，而不是抛出原始的 HTTP 错误
- 饮食的**照片分析**使用同一个端点：图片以 OpenAI 兼容的 `image_url` content part 形式装在 data URL 里发送，模型自己对不确定之处的表述会原样显示在估算结果旁边（模型生成的文字从不翻译）

**备份与恢复**
- 导出一个可读的 JSON 文件：训练、动作、组、别名规则、总结、饮食、提醒、计划和设置（单位、主题、语言、AI 端点、模型和视觉覆盖），资料填写过的话也包括它
- 饮食照片刻意不包含在内 —— 备份是你数据的记录，不是照片堆。恢复后的一餐保留数字，没有图片
- API Key **绝不会**写进备份，恢复也绝不会覆盖设备上已有的 Key
- 导入前先校验文件，显示里面有什么、会替换掉什么，确认之后才应用。在饮食、提醒和计划出现之前导出的备份仍然可以导入：其中的训练原样恢复，较新的部分是空的
- **Markdown** 和 **CSV** 导出便于阅读：每个动作一张表、每一组一行，以及每行一组的 CSV，规范 kg 值与显示重量并列。CSV 单元格会加前缀，电子表格无法把输入的文本当成公式执行。范围可选全部时间、本月或最近 7 天。

**设置**
- 语言：**自动**（跟随系统）或简体中文 / English / Español，切换立即生效，无需刷新。日期和时间格式跟随所选语言
- 主题：四套内置主题 —— **ragdoll**（布偶猫，暖白与粉色）、**bunny**（兔子，粉蓝）、**panda**（熊猫，黑白）和 **orca**（虎鲸，深海蓝）—— 各有自己的配色和 16×16 像素吉祥物，选择器里以色块加吉祥物展示。在 Android 上状态栏跟随主题，图标颜色由状态栏底色推导，而不是按每套主题写死
- 默认单位（kg / lb）
- 显示当前使用的存储引擎，保持透明
- AI：启用开关、Base URL、Key、模型、默认角色，以及检测到的视觉能力和覆盖开关
- 通往个人资料、备份与恢复、训练总结和别名规则的入口
- 删除全部本地数据（训练、饮食、总结、规则和资料）

### 单位

重量按你输入的数值加上它的单位存储，同时保留一个规范的 kg 值，用于容量计算和比较。切换显示单位不会改写你的历史。

### 语言与主题

所有用户可见的文案都来自翻译目录：`src/i18n/en.ts` 是基准，`zh-CN.ts` 和 `es.ts` 按它的结构做类型检查，所以漏掉或拼错的键是构建错误，而不是中文界面里冒出一个英文单词。日期、时间和数字格式化统一走 `Intl`，并使用该语言自己的 locale 标签。模型生成的文字 —— AI 的回答、饮食估算自带的说明 —— 原样显示，从不翻译。

一套主题是一组颜色 token、一个像素吉祥物**和一组景物图案**。组件只消费 token，样式表里没有自己的配色值，所以新增第五套主题只需要加一个 `ThemeDefinition`、一个 16×16 吉祥物精灵和几个图案 —— 不用改页面、组件或样式表。所有图形都以字符网格的形式用代码绘制：应用里没有任何图片文件、base64 数据块或第三方素材，应用图标和启动画面也一样。

四套主题是 **ragdoll**（应用自己的猫：暖白纸感、灰色毛发、蓝眼睛、粉色鼻子）、**bunny**（粉蓝）、**panda**（黑白）和 **orca**（深海蓝）。

#### 主题景物

主题不只是换个配色，它还会用属于自己的东西装饰界面：

| 主题 | 地面条带 | 立在上面 | 空中 |
| --- | --- | --- | --- |
| ragdoll | 柔软的草 | 一个爪印、一团毛线、一颗心 | 纸片云、一颗心 |
| bunny | 一簇簇草 | 一朵花、一根胡萝卜、一颗心 | 一朵云、一颗心 |
| panda | 低矮的苔藓 | 一根竹子、一个爪印、一片叶子 | 一片叶子、一个爪印 |
| orca | 水面与浪尖 | 一条鱼、气泡、一颗星 | 气泡、一颗星 |

图案在运行时合成成一整条宽精灵图（`src/theme/scenery.ts`），画在首页主卡片的底部和空状态里。三条规则让它只是装饰而不是噪声：它是 `aria-hidden`，从不接收点击，排列是确定性的 —— 同一套主题永远画出同一个场景。浏览器冒烟测试会比较三套主题场景的像素级指纹，所以「每套主题画自己的景物」是被断言过的，而不是假设的。

### 应用图标

启动图标是手绘的布偶猫，直接使用原始素材：
`design/icon-candidates/source/cat-sketch.jpg`（413×358）。处理流程把它裁成 350×350 的正方形，保留整只猫，去掉右边缘的心形和另一幅画的残片，从四角采样草图自己的纸张颜色（`#f9f5f2`），再把结果按各密度合成。

```bash
pwsh -File design/icon-candidates/render-android-icons.ps1   # launcher + adaptive layers
node design/icon-candidates/render-splashes.mjs              # splash, both orientations
```

有三个决定值得说明：

- **这幅画是自适应图标的*背景*层，不是前景层。** 草图是没有透明通道的 JPEG，如果当前景层用，它自带的白色方块会压在背景色上，接缝会露出来。让它在背景层满幅铺开，启动器遮罩裁掉的是纸张而不是猫，`ic_launcher_foreground.png` 则是一张透明占位图。
- **猫占普通方形图标的 88%、圆形图标的 78%、自适应图层的 78%。** 自适应安全区是 108dp 中间的那 72，圆形遮罩内切于其中；取 78% 时耳朵、眼睛和鼻子始终落在安全区内。按圆形裁切的启动器会剪掉最外侧的胡须 —— 草图是画到边的，否则猫就会显得缩在正中间。
- **这幅画在进来的路上被稍稍加深**（gamma 取 1.35）。它是一张很淡的铅笔稿，在 48px 下毛发会和纸色糊在一起。Gamma 压暗中间调 —— 毛发和轮廓线 —— 同时不动接近白色的纸面；换成对比度曲线会恰好相反，把浅灰的毛发进一步推向白色。填充色随后从调整后的图上重新采样，让平铺色块和裁剪边缘完全吻合。

`design/icon-candidates/preview-icons.png` 展示了结果在 Android 使用的三种遮罩形状下的样子，用 `node design/icon-candidates/preview-icons.mjs` 可以重新生成。

`design/icon-candidates/alternates/` 放的是一只和像素吉祥物同风格的矢量猫；那是最早的尝试，只作参考保留。`uc-monogram/` 放的是更早的字母造型方案。

### 布局

同一套布局要服务小屏手机、长屏手机、折叠与展开状态的折叠屏、平板、横屏手机和接近桌面宽度的窗口。手机上是底部导航栏，56rem 以上换成侧边栏；字号使用流式 `clamp()`，栅格用 `auto-fit`，内容有最大阅读宽度，空间够时会居中，弹层在宽屏上变成居中对话框而不是满宽面板。内容宽度没有写死的像素值。浏览器冒烟测试会在手机视口和桌面视口下各跑一遍完整用例，并在每种宽度下断言只显示一个导航、没有任何横向溢出。

### 圆角

界面由圆角对象搭成，而不是切角的矩形，整体圆角来自 `:root` 里的六个 radius token：

| Token | 用途 |
| --- | --- |
| `--radius-xs` | chip、分段按钮、对话气泡内侧的角 |
| `--radius-sm` | 输入框、横幅、内部区块、卡片里嵌套的卡片 |
| `--radius` | 卡片、动作卡片、主题磁贴 |
| `--radius-lg` | 卡片外圈、聊天气泡、文本输入框 |
| `--radius-xl` | 底部弹层的顶部 |
| `--radius-pill` | 所有按钮、徽章、开关和筛选 chip |

嵌套表面会**向下**降一档（卡片用 `--radius-lg`，它里面的元素用 `--radius-sm`），让曲线保持同心；嵌套盒子用相同圆角会显得内侧更紧，看起来不对。`src/test/theme.test.ts` 并不检查这一点，但 `global.css` 里没有任何字面量圆角值 —— 界面上每个圆角都来自上面这张表。

### 数据模型一览

`Workout → ExerciseEntry[] → SetEntry[]`，其中一组带有重量、次数、可选的时长、距离、休息、RPE、RIR，以及力竭/热身/递减组的标记。饮食是另一个聚合：`Meal → MealItem[]`，一餐的总量由其明细项推导。完整模型和取舍见 [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)。

## 已知限制

- **没有在真实硬件上跑过。** APK 在这个环境里没有装到真机或模拟器上（没有安装系统镜像）。SQLite 适配器的测试会通过伪插件执行它真实的 SQL，但在设备上做第一次启动仍然值得。
- **原生路径只做了类型检查，没有真正跑过。** 分享面板和文件选择器（`services/fileTransfer.ts`）是按 Capacitor 的 `@capacitor/share` 和 `@capacitor/filesystem` 定义写的；相机/相册选择器（`services/imageInput.ts`）是带 `capture="environment"` 的平台文件输入，Android WebView 会把它接到系统选择器上。硬件上没有任何原生对话框被打开过。它们周围的浏览器降级路径确实在冒烟测试里跑过，但无头页面驱动不了原生对话框，所以那一轮是通过仓储写入饮食照片，而不是走选择器。
- **两个 Android 外壳集成同样没有在硬件上验证过。** `services/nativeShell.ts` 按当前主题给状态栏上色，并接管硬件返回键（关闭弹层 → 返回上一页 → 在起始页退出）。两者都由 `Capacitor.isNativePlatform()` 保护，所以在浏览器里不生效；状态栏的*判断逻辑*也有单元测试，但没有人在设备上见过它们工作。
- **没有调用过真实模型。** 这个仓库从未连过任何 LLM 或视觉端点：OpenAI 兼容客户端是对着 mock 的 `fetch` 测的，饮食分析由注入 chat 函数的测试覆盖。因此某个端点是否接受 data URL 图片，是靠能力规则和处理端点的拒绝来验证的，而不是靠一次真实请求。
- **启动图标没有在真实启动器里看过。** 素材的验证方式是在 48、96 和 192 px 下渲染出来用眼睛看，自适应前景也按文档给出的安全区缩放过，但具体某台手机用哪种遮罩（圆形、圆角方形、方形），以及状态栏颜色挨着真实的 Android 主题是什么效果，目前只能从平台规则推断。
- 浏览器冒烟测试需要安装 Chrome 或 Edge；没有的话 `npm run test:browser` 会提示跳过，并以成功状态退出。

## 应用改名：哪些标识被冻结

产品名在 0.8.0 从 *Fitness Agent* 改成 *FitAGI by Capy*。有四个标识刻意**没有**改，因为它们决定既有数据怎么被找到，而不是应用怎么介绍自己：

| 冻结值 | 位置 | 原因 |
| --- | --- | --- |
| `fitness-agent-backup` | `services/backup.ts` | 用来识别备份文件的标记。改掉它会让用户已经导出的每一份备份都被拒绝。 |
| `fitness-agent` | `storage/idbAdapter.ts` | IndexedDB 数据库名。改掉它会悄悄打开一个全新的空数据库。 |
| `fitness_agent` | `storage/sqliteAdapter.ts` | Android 上的 SQLite 文件名，原因同上。 |
| `app.fitnessagent.tracker` | `capacitor.config.ts`、`build.gradle` | Android 包名。换一个会装出第二个应用，并把第一个应用的数据留在原地。 |

用户实际看到的文件名 —— 备份、Markdown 和 CSV 导出 —— 确实改了，改成 `fitagi-2026-02-14-0931.json`、`fitagi-2026-03-04.md` 和 `fitagi-2026-03-04.csv`。那些是标签，不是键：旧文件仍然能恢复，因为格式是从内容判断的。

## 出问题时怎么办

渲染出错时显示的是恢复界面，而不是白屏 —— 用你选择的语言 —— 并明确说明你的数据没有被动过。如果反复出现，打开数据页（在地址后加上 `#/data`）导出一份 JSON 备份 —— 那才是可以恢复的格式。

## 本阶段不包含

一些能接进现有结构里的想法：定时重建每周总结、在力量曲线旁边加一条按动作的容量曲线、一个用来对照当天摄入的营养目标，以及进度照片。这些都不需要改动架构。

## 隐私

所有数据都在这台设备上。没有项目服务器，没有账号，也没有埋点。应用唯一可能发出的网络请求，是发往*你*配置的 OpenAI 兼容端点，而且只在你主动触发 AI 操作时。每条 AI 回答都会显示这次发送了哪些上下文段落，饮食照片也只会在你发起的那次分析请求里发送 —— 它不会被上传到别处，并且留在应用自己的存储里。个人资料只存在本机，只有作为附在饮食请求后的简短上下文块时才会到达模型。备份里永远没有你的 API Key，也没有饮食照片。
