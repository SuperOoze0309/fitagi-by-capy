## DS-01 · P1 · SQLite 初始化违反原生插件的连接契约

- **证据等级：原生源码 + 契约替身复现；未上真机。** `src/storage/sqliteAdapter.ts:41` 先调用 `isDBExists`，只有返回 false 才 `createConnection`。安装的插件原生实现 `CapacitorSQLite.java:1049` 的 `isDBExists` 本身要先从 `dbDict` 取连接；没连接时就抛错。`open` 也要求连接。现有 `FakeSqlitePlugin.ts:59` 不检查这个前置条件。
- **实际输出：** 新插件会话的调用只有 `["isDBExists"]`，随后 `No available connection for database fitness_agent`。`src/storage/index.ts:40` 捕获 SQLite 初始化错误后转到独立 IndexedDB，可能把原生错误隐藏成空数据界面。
- **要求：** 区分数据库文件和进程内连接的生命周期；按真实插件契约建立/复用连接，再查询、打开和建表。不要用文件存在与否判断连接是否已注册。让替身忠实检查调用顺序。检查已有 SQLite 数据时的 fallback 行为，避免静默切到另一份数据而没有明确恢复方式。
- **验收：** 新安装、已有文件冷启动、close/init、并发启动、v3 → v4 都覆盖；原数据和聊天保留。真实 APK 冷启动若仍无设备条件，必须写成未验证，不能把替身通过说成真机通过。

## DS-02 · P1 · 恢复先清空再写，失败会丢原数据

- **证据等级：隔离复现。** `src/services/backup.ts:252` 清空六类记录，`259` 起才写入；没有跨集合/资料/图片的事务或回滚。
- **复现：** 放入一条训练，构建备份，再让 `training.putMany` 抛 `INJECTED_WRITE_FAILURE`，调用 `applyBackup`。异常后原训练数量从 1 变为 **0**。饮食清空还会删除原照片。
- **要求：** 恢复必须是完整提交或原数据保留；先校验和准备所有记录，协调跨 store 的写入及缓存。浏览器端真实 IDB 事务、Android 端事务/可恢复的替换方案都要考虑。只在 catch 里提示错误不算修复；内存回滚若可能再次失败，也不能冒充持久化原子性。
- **验收：** 在各集合清空、各写入阶段、图片/资料/设置阶段注入失败；训练、照片、资料、设置、聊天取舍保持约定，缓存与磁盘一致。成功恢复仍兼容旧备份。

## DS-11 · P2 · SSE 不支持 CRLF，遇到 DONE 仍等连接关闭

- **实际输出：** destroyStorage → initStorage(new adapter) 返回旧 bundle，再 getStorage 报未初始化。另一个连接保持打开时，destroy Promise 已 resolve，但旧连接仍能读到 **1 条**。
- **要求：** 完整重置 bundle、初始化 Promise 和仓储缓存引用；数据库删除只在真实完成后成功，blocked 要明确处理，不可以假装删除。协调重入及失败重试。
- **验收：** init/destroy/init 正常；双连接删除阻塞、另一端关闭、销毁失败、并发初始化都覆盖。当前 Settings 的删除没有调用 destroyStorage，不能声称这个库级问题已在按钮路径复现。

## DS-19 · P2 · IndexedDB 的超时保护没有覆盖聊天/设置等 KV 操作

- **验收：** 对 pending IDB request/transaction 注入不完成；聊天 historyReady、保存、清空以及启动设置读取都能进入错误/重试状态，释放 timer/transaction。与 DS-02 的恢复原子性协调。

## DS-22 · P1 · 聊天历史读取失败后，新回答会覆盖未知旧历史

- **证据等级：静态入口 + 仓储调用链隔离复现；未渲染组件。** `AiPage.tsx:75` catch 后 finally 仍 historyReady=true，空 exchanges 可继续发问；`saveConversation` 用全量快照替换仓储。
- **实际输出：** 原有一条 old，注入一次 recent 读取失败，随后按 UI 同一策略保存 new+空历史；最终 storedIds 只剩 **[new]**，旧问答丢失。
